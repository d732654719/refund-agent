# 文档随代码维护

## 每次变更怎样做

1. 从项目 `AGENTS.md` 进入相关模块说明，再查看链接的代码和契约测试。发现文档与代码不一致时说明差异；不要把实现缺陷自动改写成业务规则。
2. 修改职责、公共接口、状态/异常语义、依赖或运行命令时，在同一变更中更新最近的说明。纯内部重构且契约不变时，可以不改文档，交付时说明理由。
3. 字段、默认值、状态枚举等由代码或 Schema 定义；文档解释用途、边界和验证入口，避免复制第二份数值表。
4. 删除无法对应具体决策的句子，合并重复约束；详细机制下沉到模块，入口保留项目定位、运行、验证和导航。
5. 执行下面的本地检查，并按复核问题确认地图可用。最后报告文档更新或无需更新的理由，以及实际验证范围。

项目事实保存在仓库内，聊天记忆只作查找线索。计划文档描述目标，历史记录描述当时结果；它们不能证明当前实现和当前验收。业务目标与代码冲突时，需要结合用户需求和契约测试判断应修代码还是修文档。

## 本地与 CI 检查

在本仓库根目录执行：

```powershell
.venv\Scripts\python.exe scripts/check_docs.py
# 检查某个基线以来已经提交的变化时，传入实际基线
.venv\Scripts\python.exe scripts/check_docs.py --base <实际基线提交或分支>
```

独立检出时换用本机 Python 3.10+。脚本只用标准库和 Git，不调用模型、不读取密钥，也不修改文件。
默认比较 HEAD 与本地暂存/未暂存改动并包含未忽略的新文件；`--base` 比较该基线与 HEAD 的共同祖先到 HEAD，只检查已提交变化。

[检查脚本](../scripts/check_docs.py) 检查所有版本管理范围内的 `AGENTS.md` 及本文件中的普通 Markdown 本地文件链接、必需入口和空文档。代码块、网址、锚点目标和复杂 Markdown 语法不属于链接检查范围；它不会判断链接中的函数是否仍存在，也不会判断文字是否准确。
代码或配置变化时，查找最近的 `AGENTS.md`；该入口未变化就提醒复核。改了说明也不代表语义已正确，需要继续做人工或 Agent 审阅。超过 100 行只提醒精简，不为达到最低行数填充内容。

[GitHub Actions](../.github/workflows/documentation.yml) 在 PR 或手动触发时执行相同检查。断链/必需入口错误返回失败，模块复核提醒不阻断。相关文件提交并推送到启用 Actions 的仓库后才会运行；本地验证不代表远端 CI 已运行。
无需更新文档时，在交付说明或 PR 中写出具体依据，例如“仅调整内部循环，接口、状态和运行入口未变”，不要靠改一行无关文字消除提醒。

## 新会话复核

新会话只读仓库文件，从项目入口回答以下问题，并指出代码或测试依据；不使用聊天记忆补答案。当前会话按表检查只能叫导航复核，不能称为已完成独立新会话测试。
遇到问题没有答案时补到最近的模块；答案重复时合并；已不影响决策的问题删除。无需固定每次全量重测，地图或职责发生变化时复核相关问题。

| 问题 | 答案入口 |
| --- | --- |
| 应在哪个分支修改，如何避免导入另一分支？ | [项目入口](../AGENTS.md) |
| 订单归属与金额由谁检查，为什么创建退款还要重查？ | [运行模块](../refund_agent/AGENTS.md) 的业务工具与政策入口 |
| 无业务工具调用时怎样结束，已退款后异常怎样报告？ | 运行模块的分支协议和 `_complete_result()` |
| 改状态或工具结果需要同步什么？ | 运行模块的状态目录、[状态指南](../agent_status_guide.md) 与 [评测模块](../agent_evaluations/AGENTS.md) |
| 报告 JSON 谁组装，HTML 应改哪里？ | 评测模块的 session/writer 与项目的共享依赖说明 |
| 哪些测试离线，哪些会调用模型？ | [单元验证](../unit_tests/AGENTS.md) 与评测入口 |

## 谁负责

执行代码变更的 Agent 可以同步文档、发现重复、补充缺失导航并说明依据；CI 负责机械检查和提醒。业务目标、预期结果或职责发生实质变化时，由用户确定意图，Agent 负责按决定落实。
原则“最小但完备”和“随代码更新”是每次变更的操作过程，不能靠首次生成文件永久保证。规则只记录会影响决策的内容，不以文档数量或字数作为质量证据。
