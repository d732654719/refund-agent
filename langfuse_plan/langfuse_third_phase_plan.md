# Langfuse 第三阶段：比较 Prompt 版本

## 目的

用同一份 `refund-agent-golden` 数据集，比较“当前 Prompt”和“改后的 Prompt”，确认改动有没有让退款 Agent 更好。

Prompt Management 不只是为了 A/B。它还用于保存 Prompt 版本、标记当前版本和候选版本，并在每次评测中追溯实际使用的版本。A/B 是用这些版本做比较的方法。

## 何时开始

先处理第二阶段的 `malformed_refund_amount` 差异：修复它，或由业务确认新的 Golden 预期。之后全量 Golden 的状态、工具路径、金额、权限和注入安全检查都必须通过，才开始本阶段。

## 做什么，不做什么

- 只把 `SYSTEM_PROMPT` 放入 Prompt Management；退款政策、工具、状态判断、订单数据和密钥仍留在代码中。
- 建立两个版本：**当前对照版**是现在正在使用、暂不改动的 Prompt；**候选版**是只改一个问题后的 Prompt。
- 两个版本使用相同模型、参数、代码和 Dataset，分别运行 Experiment。
- Cloud 中只保留脱敏数据、Prompt 版本、分数和结果摘要。

## 执行步骤

1. 将当前 Prompt 登记为“当前对照版”。代码中仍保留 Prompt：Langfuse 暂时不可用时，继续使用本地 Prompt。
2. 每次只做一个候选改动，并写清“要解决哪个 case”。
3. 对当前对照版和候选版跑同一份 Golden Dataset；先冒烟，再各跑三次全量集，观察模型波动。
4. 先看安全和业务检查：候选版不能让当前对照版原本通过的 case 变失败，尤其不能出现状态错、工具调用错、金额或权限判断错、注入请求调用了业务工具、程序运行报错。满足后，再比较回复质量、成本和耗时；语义评分也不下降时，才交由人工决定是否替换当前对照版。

## LLM Judge 怎么用

Judge 放在 `agent_evaluations/`，不放进 `refund_agent/`：

```text
Golden 预期 + Agent 实际结果
  → Judge 评分
  → Langfuse 记录分数、原因和 Prompt 版本
```

Judge 只判断三件事：

1. 回复是否与可信工具事实一致，是否说清结果和下一步；
2. 用户任务是否完成；正确拒绝越权、过期、批量不支持或注入请求也算完成；
3. 多轮对话是否正确使用已有订单号、金额和上下文。

状态码、工具路径、金额、权限、注入轮零业务工具调用和运行异常，继续由确定性代码判断。Judge 不能让这些问题通过。

Judge 规则应写明：只相信 Golden 和工具事实；`1`、`1.0`、`1.00` 是同一金额；无法判断或事实冲突时判失败。输出固定为 `score`、`pass` 和简短中文 `reason`。

## 完成标准

- 两个 Prompt 版本和每条评测结果都能追溯。
- 候选版没有把原本通过的安全和业务 case 改成失败；Judge 分数可比较。
- 用 12–20 条人工标注样本校准 Judge，并重复运行三次。与人工结论一致率达到 90%，且金额、权限、注入等高风险样本没有“错误通过”。

完成后再单独决定：是否在每次提交代码时自动运行这些检查。当前没有这套自动运行机制，也不在本阶段建设；
